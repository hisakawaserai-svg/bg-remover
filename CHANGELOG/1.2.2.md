## 未着手

### 自動分割画面: 「分割の細かさ」を廃止し「自動除去の強さ」に入れ替える

見つけた問題:

- 自動分割で背景がうまく抜けない場合、設定画面の「自動除去の強さ」を変える必要があるが、それがどこにも書かれておらず気づけない
- 設定で値を変えても、今の画像は再処理されない（`processImage` の最初に1回だけ `appSettings.tolerance` を読むため）。画像を選び直すまで反映されない
- 「分割の細かさ」スライダーは実際に使ってみると不要だった。行数・列数のステッパーで直接調整する方が早い

- 分割の行・列を追加した際に線の配置がリセットされる。

方針: 「分割の細かさ」（`splitTolerance`）スライダーは完全に廃止する（設定画面にも移さない）。空いた場所に「自動除去の強さ」の調整を置く

コミット分割（1コミット1変更）:

1. SetupScreen から「分割の細かさ」スライダーを削除
   - `bgVersion` の effect 内の `recalcCols` は、保存済みの `splitTolerance` ではなく既定の定数で `detectColCount` を呼ぶ（App.tsx の初期推定 3 か所がしきい値を渡さず既定の定数を使っているのに合わせる。過去にスライダーを動かしたユーザーの保存値を使うと、初期推定とスポイト後の再推定で基準がズレるため）
   - `store.ts` の `splitTolerance` キー、`toleranceToGapParams`、i18n の文言は残す（既存の保存データとテストへの影響を避けるため）
   - `colsManualRef` は列ステッパーでも使うので残す
   - 実機確認: 初期の行数・列数が今まで通りか / スポイト後に再推定されるか / 列ステッパー手動操作後にスポイトしても壊れないか
2. 空いた場所に「自動除去の強さ」を追加。以下は未決定:
   - Vision（被写体検出）で除去した場合、`tolerance` は結果に影響しない（Vision の結果で `rgba` を丸ごと置き換えるため）。Vision 時にスライダーを出すか、どう出すか。SetupScreen はどのエンジンで処理したかを今は受け取っていない
   - 再処理時にスポイト等の編集（`editsRef`）を捨てるか、確認を出すか
   - 変えた値を設定にも保存するか（「この画像だけ」か「次からも」か）
   - 再処理は `restartWithDifferentEngine` と同じく `processImage` を呼び直す経路が使える。ただし `processImage` はクロージャ経由で `appSettings.tolerance` を読むので、新しい値は引数で明示的に渡す（古い値のまま再処理される恐れがある）
   - UI は設定画面と同じ `ToleranceSlider` に `REMOVAL_SNAPS` を渡す形が候補

### 背景が透過されたことが分かりづらい

- 完了トースト（`setup.bgRemoved`）は数秒で消えるので、見逃すと市松模様の意味が分からない
- 画面に残り続ける手がかりが必要
- 候補: SetupScreen はすでに `originalImageUri` を受け取っているので、元画像との before/after 比較（長押しで元画像表示など）
- 上の「分割の細かさ」→「自動除去の強さ」が終わってから、別コミットで対応する
